## 3）推荐的系统架构
可以按这层来搭：

### A. 数据层
从 U8 拿数据，常见方式：
- 直连 **SQL Server**
- 读取现有报表/中间表
- 调用 U8 开放接口（如果你们环境有）

建议优先：
- **只读账号**
- 建一层 **业务视图 / 中间表**
- 不让 AI 直接读特别底层、特别散的原始表

也就是：
> U8 原始表 → SQL 业务视图/数据服务 → AI 助手

这样后面维护会轻松很多。

---

### B. 业务规则层
这一层很关键，别全交给大模型。

比如：
- 什么叫“可交付”
- 什么叫“采购在途”
- 交期怎么推算
- 安全库存怎么判定
- 全月平均价怎么解释
- 哪些状态属于异常

这些都应该写成：
- SQL 规则
- Python/Node 规则
- 配置化规则

AI 负责：
- 理解问题
- 调用工具
- 汇总结果
- 用自然语言解释

也就是：

> **确定性规则 = 程序**  
> **模糊解释 = AI**

这是成败关键。

## 5）落地时最容易踩的坑
我直接说几个最常见的。

### 坑一：一开始就想做全模块
结果范围太大，最后每个模块都半成品。

**建议：只打一个闭环。**  
比如先做：

> 销售订单交付分析 → 缺料判断 → 采购在途追踪 → 生成交期回复

这个闭环做成，就已经很有用了。

---

### 坑二：把 AI 当数据库本身
AI 不能代替清洗过的数据模型。

如果底层数据关系乱、口径不统一，AI 只会把混乱说得更像那么回事。

所以一定先做：
- 指标口径统一
- 核心 SQL 固化
- 关键字段字典化

---

### 坑三：没有权限隔离
不同岗位看到的数据不一样：

- 销售能看订单
- 采购能看供应商与到货
- 财务能看成本
- 老板能看汇总
- 普通员工不该看到敏感价格

所以助手一定要做：
- 账号权限
- 数据范围控制
- 操作日志

---

### 坑四：回答“像对的”，但其实不准
所以要让回答尽量带上：
- 数据来源
- 截止时间
- 判断依据
- 不确定项

比如：
> 截至 2026-05-20 09:30，物料 A 当前可用库存 80，在途采购 200，最近到货承诺为 2026-05-24；若供应商按期交货，则订单 SOxxxx 大概率可满足首批出货。

这种就靠谱很多。

# 一个很关键的设计：不要把“知识搜索”和“业务查询”混为一谈
这个坑很大。

## 知识搜索
回答的是：
- 有什么文档
- 某规则怎么写
- 某流程怎么做
- 某 SQL 在哪
- 某历史经验是什么

## 业务查询
回答的是：
- 这个订单现在什么状态
- 这个物料库存多少
- 这个采购单为什么没到
- 这个客户最近出货多少

前者靠知识库索引，后者靠系统接口 / SQL / 报表服务。

所以企业知识库第一阶段建议只聚焦：

> **让人“找得到、看得懂、能追溯来源”。**

而不是立刻承担实时业务问答。

# 现在最需要先定的 8 个规划项
我建议我们一起先把这 8 个问题定下来：

## 1. 目标用户是谁
比如：
- 管理层
- 销售
- 采购
- PMC
- 财务
- IT/数据团队

不同用户决定了入口和权限策略。

## 2. 第一阶段纳入哪些来源
建议只选 3~5 个，别太多。

## 3. 每个来源的更新方式
- 定时全量
- 增量同步
- 手动触发
- 事件触发

## 4. 每个来源的权限边界
- 全员可见
- 部门可见
- 指定角色可见
- 敏感信息脱敏

## 5. 检索结果的权威排序规则
比如：
1. 制度/SOP
2. Wiki 归档知识
3. 业务沉淀文档
4. 文件服务器普通资料
5. 临时聊天记录

## 6. 是否需要版本与失效机制
同一份制度有多个版本怎么办，这是大坑。

## 7. 搜索不到时怎么处理
- 返回相似内容
- 建议去哪个系统找
- 提供“发起补充知识”入口

## 8. 第一阶段成功标准是什么
例如：
- 常见问题 70% 能搜到
- 搜索响应 < 5 秒
- 前 3 条结果命中率高
- 业务人员愿意持续使用

按 **采购发票金额** 查询采购发票记录。

```sql
SELECT
    a.ID,
    a.cPBVCode AS 发票号,
    a.dVouchDate AS 发票日期,
    a.cVenCode AS 供应商编码,
    v.cVenName AS 供应商名称,
    a.cDepCode AS 部门编码,
    a.cMaker AS 制单人,
    a.iTaxRate AS 税率,
    a.iSum AS 原币无税金额,
    a.iTax AS 原币税额,
    a.iMoney AS 原币价税合计,
    a.iNatSum AS 本币无税金额,
    a.iNatTax AS 本币税额,
    a.iNatMoney AS 本币价税合计
FROM PurBillVouch a
LEFT JOIN Vendor v ON a.cVenCode = v.cVenCode
WHERE 1 = 1
    -- 按本币价税合计金额查
    AND a.iNatMoney = 1000
ORDER BY a.dVouchDate DESC, a.cPBVCode DESC;
```

## 如果你想查“某个金额附近”的记录
因为金额有时会有小数，建议用区间：

```sql
SELECT
    a.cPBVCode AS 发票号,
    a.dVouchDate AS 发票日期,
    a.cVenCode AS 供应商编码,
    v.cVenName AS 供应商名称,
    a.iNatSum AS 本币无税金额,
    a.iNatTax AS 本币税额,
    a.iNatMoney AS 本币价税合计
FROM PurBillVouch a
LEFT JOIN Vendor v ON a.cVenCode = v.cVenCode
WHERE a.iNatMoney BETWEEN 999.99 AND 1000.01
ORDER BY a.dVouchDate DESC;
```

## 如果你要模糊按“含税金额 / 无税金额”分别查
